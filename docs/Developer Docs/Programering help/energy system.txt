Create Expansion energy system
==============================

Model
-----

CE uses GTCEu-style packet transfer:

`transferred CE = voltage * accepted amperage`

Voltage is the size of one packet. Amperage is the number of whole packets transferred during one
game tick. Cables never store CE; machines, hatches, and generators own bounded energy containers.
Recipes consume or produce CE/t from those buffers independently of network packet transfer.

The CE variation is deliberate: every cable is lossless. Packet voltage is unchanged across any
valid route. There is no `lossPerBlock` and Jade does not show loss.

Values use `long` throughout the transfer and storage APIs so later voltage tiers do not overflow.

Voltage and buffers
-------------------

`MachineTierStats.ceTier` starts at 8 CE for ULV and multiplies by four per tier:

- ULV: 8 CE
- LV: 32 CE
- MV: 128 CE
- HV: 512 CE
- EV: 2048 CE
- IV: 8192 CE

Standard machine and hatch buffers hold 64 packets at their tier voltage:

`capacity = voltage * 64`

Standard CE storage accepts or emits 1 A. Specialized sources, consumers, and creative blocks can
declare higher amperage.

Container input
---------------

`CEEnergyContainer.acceptEnergyFromNetwork(side, voltage, amperage)` returns the whole number of
amps accepted. `CEEnergyStorage` tracks all accepted amps for the current game tick, so multiple
sources cannot independently exceed the same input amp limit.

Accepted amps are:

`min(offered amps, remaining input amps this tick, free buffer / packet voltage)`

If packet voltage exceeds the consumer input voltage, the consumer's overvoltage action runs and
the offending amps are treated as used without being stored.

Source output
-------------

A source can offer:

`min(stored CE / output voltage, output amperage)`

It checks output sides and deducts `accepted amps * output voltage` only after a destination reports
successful acceptance. Directly adjacent containers and cable networks use the same packet API.

Cable capacity
--------------

Existing CE cable amperage rules are intentionally retained:

`max amps = ceBaseAmps(cable tier) * thickness.baseAmps()`

Existing insulated cables also retain their current doubled amp capacity. This differs from GTCEu
but is part of CE's established cable progression.

Thickness base values are 1 A, 2 A, 4 A, 8 A, and 16 A.

Routing
-------

`CEEnergyNetwork` caches routes from a source cable to reachable input containers and invalidates
the cache when cable topology changes. Routes are sorted by cable count.

Only a successful transfer is recorded. Every cable in the selected route receives the exact
accepted amp count and source packet voltage. Machine recipe demand is never broadcast across the
whole network and cannot create fake Jade flow.

There is no voltage loss. If an over-tier packet enters a cable, the cable heats and the packet
delivered beyond that unsafe cable is capped to the cable voltage. This keeps GTCEu-style fuse
behavior without distance loss.

Cable safety
------------

`EnergyWireBlockEntity` records the total real amperage for each tick.

- Overamp heat: `(current tick amps - max amps) * 40`.
- Overvoltage adds heat based on voltage tier difference.
- Ambient temperature: 293.
- Insulation can burn away at or above 1500.
- Cable melts into fire at 3000.
- Hot cables cool gradually when no new heat is queued.

When insulation burns away, the block changes to the matching existing uninsulated cable while
preserving tier, thickness, connections, disabled sides, and temperature.

Jade
----

Cable Jade matches GTCEu's information shape:

Active cable:

`Voltage: LV / LV`
`Amperage: 1.5A / 4.0A`

Inactive cable:

`Voltage: LV`
`Amperage: 4.0A`

Hot cable:

`Cable overloaded: 37%`

Current voltage is the highest actual packet voltage recorded for the current tick. Current
amperage is the average of real transferred amps over the last 20 ticks. Maximum voltage and
amperage come from the cable itself. Amperage is never derived from recipe CE/t or scanned machine
demand.

Machine and hatch Jade uses a yellow progress element:

`Energy: stored / capacity CE`

Recipe progress remains a separate Jade element owned by the shared CE recipe runtime.

Core files
----------

- `energy/CEEnergyContainer.java`: long packet and storage contract.
- `energy/CEEnergyStorage.java`: bounded storage and per-tick input amp accounting.
- `energy/CEEnergyNetwork.java`: route cache and actual packet transfer.
- `energy/EnergyWireBlock.java`: cable properties, capacity, and connections.
- `energy/EnergyWireBlockEntity.java`: flow averaging and cable temperature.
- `integration/jade/CreateExpansionJadePlugin.java`: machine and cable server-authoritative display.
Jade cable flow data
--------------------
- Cable flow is read from the server-side EnergyWireBlockEntity, not inferred from stored energy.
- Like GTCEu, the server provider is registered for the BlockEntity base class, the client component is registered for the cable block, and values are sent in a cableData compound under the provider UID.
- The tooltip always shows the cable limits from the block definition if server flow data is temporarily unavailable. Missing cableData must never hide the tooltip.
- currentAmperage is the cable's measured 20-tick average from successful energy packets routed through that cable.
- currentVoltage is the voltage recorded on the cable during the current server tick.
- Cable flow is also synchronized on the block entity update tag as a client fallback if Jade's server payload is unavailable.
- Jade shows only the voltage currently flowing, or None with no flow. Amperage is always formatted as current / maximum.
- Cable temperature remains part of cable behavior but is not displayed in Jade.
- Electric singleblock machines use the CEEnergyStorage over-voltage callback. An incoming packet above the machine input tier causes a block-damaging explosion.
- Energy input and output hatches accept or emit up to 2A. Electric singleblock machines are limited to 1A.
- Both hatches and electric singleblock machines use a tier voltage x 64 CE buffer.
- Over-voltage explosions use TNT explosion interaction so they destroy the machine or hatch and nearby blocks.
- Cable block entity flow updates continue during the 20-tick averaging decay, then stop syncing once the displayed flow reaches zero.
- Machine Jade shows readable active item/fluid inputs and outputs instead of a recipe ID, plus recipe progress and the energy buffer.
- Machine Jade's server provider is registered once for BlockEntity.class and stores its payload under the provider UID, matching GTCEu's registration/data pattern.
- Electric recipe Jade shows actual runtime consumption or production as amperage at the machine voltage plus total CE/t. For example, an 8 CE/t ULV recipe overclocked in LV displays 1.0A at LV (32 CE/t).
- Cable Jade retains the most recent transferred voltage while its 20-tick amperage window is non-zero, preventing tick-order gaps from displaying Voltage: None during active flow.
- CERecipeLogic processes a newly found recipe in the same server tick. There is no empty power-consumption tick between consecutive recipes, so continuous 1A machines produce continuous 1A cable load.
- Singleblock Jade can rebuild its provider data directly from the synchronized client block entity. It does not depend on Jade server payload delivery for recipe or buffer information.
- Singleblock energy uses the exact same Jade progress element renderer as energy hatches.
- Singleblock block entity update packets explicitly include EnergyStored and the complete CERecipeLogic execution so client-side Jade fallback has current buffer, inputs, outputs, duration, progress, and runtime CE/t.
- Singleblock Jade renders Input in aqua, Output in gold, consumed CE/t in red, and produced CE/t in green.
- Recipe duration uses a red progress bar with white overlaid text. Machine energy uses the hatch-style yellow progress bar with white overlaid text.

Shared automatic machine UI
---------------------------
- MachineGuiLayout is the single source of truth for CE singleblock machine screens and CERecipeCategory in JEI.
- The automatic layout follows GTCEu's recipe capability arrangement: item/fluid inputs on the left, the selected recipe progress bar in the center, and item/fluid outputs on the right.
- Capability grids use up to three columns and expand vertically. GUI width and player inventory position are derived from the same layout.
- Machine GUI and JEI use the same 18x18 item/fluid slot textures, input/output overlays, progress texture, and coordinates.
- Input capability rows are mirrored toward the center progress widget: visually 3, 2, 1 on the first row and 6, 5, 4 on the second. Output rows remain 1, 2, 3 then 4, 5, 6.
- Fluid input and output grids use the same directional ordering as item grids.
- Create-native kinetic recipe categories and machines remain independent and are not converted to the CE automatic GUI.
